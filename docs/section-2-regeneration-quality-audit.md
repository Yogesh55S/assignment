# Section 2: Regeneration Quality, Preservation, Schedule & Extraction Audit

## Executive Summary
This document outlines the root cause analysis, architecture design, preservation guarantees, schedule calculation rules, requirement extraction safeguards, and verification strategy for **Section 2 (Category Regeneration, Schedule Regeneration, and Requirement Extraction Quality)** of the AI Interview Prep Kit.

---

## Task 1: Category Regeneration UX, Preservation, and Question IDs

### Reported Behavior & Root Cause
- **Reported Bug**: Clicking "Regenerate Category" previously caused existing questions (`q2`, `q3`, `q4`) to disappear, leaving only `q1`, `q6`, `q7`. This created the perception of data loss and confusing non-consecutive or shifting IDs.
- **Root Cause**:
  1. Lack of explicit user confirmation explaining what would be replaced versus preserved.
  2. Question filtering in earlier code did not strictly preserve user-created, edited, or pinned questions.
  3. UI displayed raw stable internal IDs (`q6`, `q7`) as main visible titles rather than friendly sequential labels (`Question 1`, `Question 2`), while stable IDs were not clearly scoped.

### Preservation & Replacement Policy
1. **Preservation Rules**:
   - Questions in other categories: **100% Preserved** (untouched).
   - Questions in the selected category are **Preserved** if ANY of the following apply:
     - `_meta.origin === "user"` (Manually added by user)
     - `_meta.edited === true` (Edited by user)
     - `_meta.pinned === true` (Pinned by user)
   - Questions in the selected category are **Replaced** ONLY if they are generated (`_meta.origin === "generated"` or default), unedited (`!_meta.edited`), and unpinned (`!_meta.pinned`).
2. **Stable ID Policy**:
   - Preserved questions keep their exact stable IDs (`q1`, `q2`, etc.) forever.
   - New generated questions receive IDs starting after the highest existing numeric ID suffix (`q<max+1>`).
   - Internal IDs do not need to be consecutive, but the UI displays friendly sequential labels (`Question 1`, `Question 2`, etc.) per category/list view, with the stable ID displayed subtly (`ID: q6`).
3. **Confirmation Dialog Specifications**:
   - Exact message: *"Regenerating this category will replace only generated, unedited, and unpinned questions in this category. Your edited, pinned, and manually added questions will be preserved."*
   - Displays: Category name, count to be replaced, count protected/preserved, note: *"Your schedule will be recalculated using the final question set."*
4. **Post-Regeneration Summary Toast**:
   - e.g. *"Technical questions regenerated. Replaced: X | Preserved: Y | Created: Z"*

## Task 2: Regenerate Schedule Clarity and Safety

### Reported Behavior & Clarification
- **User Question**: *"Regenerate Schedule per click karne se kya hoga?"*
- **Exact Behavior**:
  1. **Backend**:
     - Executes purely deterministic code via `allocateStudySchedule()`.
     - **Zero LLM / Gemini API calls are made.**
     - Inputs: current persisted requirements, current persisted questions, current `schedule.days_available`.
     - Updates **ONLY** `kit.schedule`.
     - Preserves `company_brief`, `role`, `questions`, `flashcards`, metadata, and practice progress intact.
     - Validates exact day count, valid question IDs, integer study minutes, and mandatory requirement coverage.
  2. **UI & Warnings**:
     - Confirmation Modal message: *"Regenerate schedule will recalculate only your day-by-day study plan using the current questions and priorities. It will not change your questions, flashcards, company brief, or practice progress."*
     - If unsaved draft changes exist: automatically saves or prompts save before regenerating.
     - Explanatory UI note below schedule: *"Your schedule is calculated by code using requirement priority and question difficulty. It is not generated by the AI model."*
     - Post-success toast: *"Schedule regenerated: X days, Y scheduled questions, Z total minutes."*

## Task 3: Requirement Extraction Quality & Safeguards

### Requirement Rules & Safeguards
1. **Facts Only**: Extract role title, seniority, location, and responsibilities ONLY when explicitly supported by the job description.
2. **Missing Field Fallbacks**: Missing title uses safe fallback `"Role"` or `"Unknown Role"` for thin JDs. Missing seniority or location uses `"Not specified"` or `""`. No hallucinations.
3. **Requirement IDs**: Programmatically assigned as `r1`, `r2`, `r3` in deterministic code.
4. **Priority Classification**:
   - `must`: Required, mandatory, essential, core, "you have", minimum qualifications.
   - `nice`: Preferred, bonus, plus, desired, advantage skills.
   - Avoid false `must` for ambiguous items.
5. **Kind Classification**:
   - `technical`: Languages, frameworks, databases, libraries, infrastructure.
   - `behavioural`: Mentoring, collaboration, communication, leadership, teamwork.
   - `domain`: Industry domain, specific workflows, regulatory compliance.
6. **Deduplication**: Exact duplicate requirements are removed by normalized text comparison, preserving distinct items.
7. **Thin JD Handling**: Returns thin output with an honest extraction note explaining limitations.

## Manual Verification Protocol

1. **Category Regeneration Check**:
   - Edit a question, pin another question, and add a manual question in "Technical".
   - Click "Regenerate Technical".
   - Confirm confirmation dialog displays protected vs replaced count.
   - Click Confirm ➔ Verify edited, pinned, and manual questions survive with exact same stable IDs. Unprotected generated questions are replaced with new IDs (`q<max+1>`).
2. **Schedule Regeneration Check**:
   - Click "Regenerate Schedule".
   - Confirm modal states code-calculated schedule without LLM call.
   - Confirm only schedule days/minutes update; questions, flashcards, brief, and progress remain unchanged.
3. **Question UI Title Check**:
   - Inspect question list ➔ Confirm visible header says "Question 1", "Question 2", etc.
   - Confirm stable ID is displayed subtly as "ID: q1".
